# Railspike v0.2.1 beta 1

## Changes

- Adds optional relative effort estimation, provisional R1 reference examples, and checkpoints throughout planning and implementation.
- Supports continuing host studies with standing enrollment, stable cycle identities, preserved scope revisions, and separate retrospective assessments and maintainer acceptance.
- Clarifies agent-led upgrades for copied installations and legacy source/subtree migration, including preservation and recovery.
- Includes the previous beta's known-user recovery guidance.

Effort estimation remains opt-in and independent of debug mode. Existing approvals, branching and commit requirements remain in force. Study data stays in the consuming project; no automatic upload occurs. The Mermaid documentation policy remains a separate recommendation and is not included.

## Opt in and rollback

Ask an agent to review and update the existing installation to tag `v0.2.1-beta.1` from `https://github.com/rlspk/railspike`, verifying the product commit above, preserving local edits and a recoverable prior copy, and recording old/new provenance. Identify the installation type before choosing the update procedure; do not silently convert legacy subtree bookkeeping.

Rollback uses the same reviewed procedure with the previous installed tag or commit. Preserve host study records across rollback. Default installation continues to use main; stable Latest remains `v0.1.0`.

## Stable exit criterion

Before stable promotion, review real enrolled cycles demonstrating retained initial/revised scores, honest missing checkpoints, scope/recovery handling and closeout evidence without repeated selection questions or altered approvals. Retain the prior beta's known-user recovery exit criterion: demonstrate ordinary-entry recovery for the named user/environment with appropriate evidence. Study acceptance remains explicit; calibration review does not end ongoing collection.
