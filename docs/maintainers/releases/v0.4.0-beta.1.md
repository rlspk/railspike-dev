# Railspike v0.4.0 beta 1

One-shot fixes can now retain development evidence comparable to staged Railspike cycles in one evolving record, without intermediate step approvals.

- Explicit bounded execution authorization is recorded before implementation. Questions and plan references grant no new authority; questions also do not automatically revoke existing authority.
- The record preserves intent, scope, approach, decisions, changes, verification, recovery and delivery status. Scope expansion needs renewed authorization or a linked transition to staged planning.
- One-shot cycles use a feature branch and normally a completion commit, with no separate planning commit. Explicit no-commit requests take precedence. Existing staged approval and commit requirements remain in force.
- Host study/debug policies apply independently. One-shot checkpoints preserve original estimates, scope revisions and incomplete outcomes without fabricating stages or historical approvals.

## Merge and compatibility

The maintainer explicitly requested both merging and this beta release. Product main now contains the reviewed one-shot changes and their prior beta ancestry. This is a release-specific exception to the usual policy of keeping beta branches off main: default installs from main receive the new guidance. The GitHub release is still a pre-release, and stable Latest remains v0.1.0.

Compared with v0.3.0-beta.4, this adds optional one-shot mode and its recovery/documentation contract. Compared with the previous main, it also includes known-user recovery and qualified verification reporting, optional effort-study collection with recoverable references, extended estimates enabled by default for new enrolled cycles, prominent estimate presentation and verified-only attribution, and the single-footer rule for single-pass Step 3 plans. Existing study opt-outs and historical records are preserved; ordinary small tasks can still remain outside Railspike.

## Update and recovery

Use the existing reviewed installation update process to select `v0.4.0-beta.1` from `https://github.com/rlspk/railspike` and verify the product commit above. Preserve local edits, installation source/revision records and host plan histories. No host installation is automatically upgraded.

Choose one-shot mode explicitly for bounded execution; existing staged cycles stay staged unless you authorize a mode/scope change. Do not convert old work into fabricated prospective records. Roll back through the same reviewed update process to the prior installed tag, such as `v0.3.0-beta.4`, while retaining host records. Stop an active cycle and reconcile its mode before using older instructions that lack one-shot support.

## Stable exit criterion

Review real one-shot records for evidence parity, bounded authorization, interrupted-session recovery, scope transitions and honest incomplete outcomes, including the maintainer's Kiro Web/CLI use. Confirm staged behavior remains intact and preserve prior beta criteria for effort-history recovery, attribution and known-user outcome verification. Beta publication does not claim those live-agent criteria are met.
