# Railspike v0.2.0-beta.1: release plan and decisions

Status: **planned, not yet executed**. Recorded 2026-10-15. Nothing in this document has been pushed, tagged, or published. It records decisions made in conversation with the maintainer and the steps to carry them out, in place of a full Railspike planning cycle (release operations; scope is settled and the product change was already planned and verified).

## What is being released

Product branch `feature/known-user-recovery` in `rlspk/railspike`, tip `9774132`, based on `main` at `579c0c13956be36c308e50df60b1849f9e213da6` (the `v0.1.0` revision). Four product commits (stages 2-5; stage 1 was baseline only), instruction text only:

- **Step 2:** when a request names a known user or environment, state that user's ordinary entry point and recovery condition. Evidence from another supported platform does not satisfy it.
- **Step 3:** a stage replays each reported failure as acceptance evidence; the after-checklist rejects an installer or other-platform pass. Manual guidance can be the accepted outcome.
- **Step 4:** report checks as passed, failed, blocked, pending, or inapplicable; identify reproduced baseline failures; never present a focused pass as a full or user-outcome result.
- **Failure modes:** a new section, "Passing tests did not establish the user's recovery".

Plans, replay cases, and verification records: [debug_log_process_improvements](../../plans/debug_log_process_improvements/debug_log_process_improvements_step4_implementation_summary.md).

## Decisions

| Decision | Choice | Reason |
|---|---|---|
| Version | `v0.2.0-beta.1` | By [RELEASES.md](../RELEASES.md) this is backwards-compatible new guidance: a minor change. |
| Default install | Stays `v0.1.0` | The install prompt snapshots `main`; `main` is not changed. |
| Beta channel | Annotated tag on the unmerged product branch, published as a GitHub **pre-release** | The pre-release flag keeps "Latest" at `v0.1.0`. |
| Opt-in | Ask your agent to update the installed copy to the beta tag | The README's copied-installation update procedure already preserves local edits and records the new revision. |
| Signing | Unsigned annotated tag | Permitted by the current policy; signing setup remains deferred. |
| Announcement | Release notes only. **No website announcement; no README note on product `main`.** | A README edit on `main` would make the default snapshot differ from `v0.1.0`. |
| Process | Short release runbook (this document), not a full cycle | Scope settled; verification gate below. |

## Opt-in and rollback prompts

Opt in, from the project with the installed copy:

> Review and update the Railspike copy at `docs/railspike` to tag `v0.2.0-beta.1` of https://github.com/rlspk/railspike. Use its recorded source revision to identify local changes before replacing anything. Inspect the proposed snapshot, preserve local edits and a recoverable prior copy, verify the result, and report old/new revisions and project changes. Leave staging and committing to my normal project workflow.

Roll back: the same request with tag `v0.1.0`.

## Runbook

1. **Policy.** Add a pre-release paragraph to `RELEASES.md`:
   - tags `vX.Y.Z-beta.N`;
   - made only from non-default branches, never "Latest", never moved or reused (a fix is `beta.2`);
   - promotion merges the same reviewed commit and tags `vX.Y.Z`.
2. **Notes.** Write `releases/v0.2.0-beta.1.md` in the `v0.1.0.md` format: the changes above, the exact product revision, the opt-in and rollback prompts, the evidence boundary, the exit criterion, and the unsigned-tag statement.
3. **Upgrade test (gate).** In a disposable project, install the `v0.1.0` snapshot as a copy, then give an agent the opt-in prompt. Record the results. It must show that the agent:
   - targets the tag and not `main`;
   - preserves a deliberate local edit;
   - records the new revision in `RAILSPIKE_SOURCE.md`;
   - rolls back cleanly to `v0.1.0`.
4. **Product checks.** On the product branch tip: product link checker, Git workflow fixture, `git diff --check`, and the repository-separation fixture against the candidate revision.
5. **Publish (one confirmation before the batch).**
   - Push the product branch to `origin`.
   - Create the annotated tag on its tip, unsigned.
   - Confirm the object type is `tag` and the peeled commit matches the reviewed commit; record both IDs.
   - Create the GitHub pre-release from the existing tag with `gh release create --verify-tag --prerelease`, using the notes.
6. **Records.** Commit the notes, policy paragraph, and test results in `railspike-dev`; record the product commit and tag object IDs here.

## Stop conditions

- The upgrade test shows the agent resolving "update" to `main`. Then reword the prompt or return to a short Step 2 for a README update-procedure fix.
- Any product check fails.
- `gh` is unauthenticated: stop and hand over the exact commands.
- A branch rebase is needed before promotion: tag a new commit as `beta.2`; never move a published tag.

## Exit criterion (beta to `v0.2.0`)

- At least one real planning cycle on an opted-in project, with debug mode on and the debug log reviewed.
- The new rules show no unnecessary gates on work with no named user or environment, and no missed recovery condition when one is named.
- Merge the product branch to `main` and tag the same commit `v0.2.0`.

## Evidence boundary

The three wording changes were verified by replaying recorded cases (missing PHP, missing extensions, an over-confident completion handoff, pending live checks) against the text. This is not a measurement of agent behavior. The beta exists to get live evidence, and the release notes must say so.
