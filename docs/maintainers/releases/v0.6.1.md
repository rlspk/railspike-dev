# Railspike v0.6.1

This stable release follows `v0.4.0` and collects the work from the `v0.5.0`–`v0.6.1` betas. It adds a lazy concept inventory, one implementation standard shared by staged and one-shot work, committed plans before implementation, plain-language writing rules, and a commit at each staged planning approval.

Product revision: [`3cd8580569cc6665bcdd21ca2e85422182a724e0`](https://github.com/rlspk/railspike/commit/3cd8580569cc6665bcdd21ca2e85422182a724e0). This is the same commit as `v0.6.1-beta.2`, now on `main`.

## What changed since v0.4.0

**Concept inventory**

- Railspike keeps a short inventory of project concepts under the host's `docs/concepts/`. Each entry has a name, purpose, brief scenario and source paths.
- Maintenance is lazy: a cycle creates or updates only the concepts it touches. There is no project sweep or backfill, and work with no relevant concept can say "none".

**Shared implementation standards**

- Staged and one-shot work follow one implementation contract. Agents inspect existing components, styles, helpers and API contracts before creating equivalents, and record reuse decisions.
- Completion covers the normal entry point, the end-to-end outcome and failure recovery. Agents verify affected consumers, replay reported failures and disclose missing evidence.
- The installation welcome offers host-owned engineering guidance for Direct work as well as Railspike, with consent.

**Committed plans**

- One-shot work creates a feature branch and commits its plan before implementation, then commits the implementation with the updated plan.
- Staged work commits each approved step before the agent drafts the next one. The feature branch and folder are set up at the first approval. Step 4 verifies the existing planning commits instead of creating a duplicate.
- Agents verify each planning commit. Resumed cycles disclose missing history and never invent or rewrite earlier commits. Explicit no-commit requests take precedence, keeping the branch and written plan.
- Step 1 may remind you that now is a good time to `/new` or `/clear` when earlier discussion preceded it.

**Writing style**

- Plans and handoffs share six writing rules, with a before/after example linked from each step and from one-shot instructions.

## Compatibility and migration

- Approval gates (`Approved Step N`) are unchanged. Branch, folder and planning-commit timing now follow the committed-plan rules above.
- Existing installations are not changed until you upgrade them. Use the README's reviewed upgrade process and select `v0.6.1`, preserving local edits and the installation source record.
- In ongoing cycles, save currently approved plans before dependent work. Disclose missing history instead of fabricating it.
- Host `AGENTS.md` or `CONTRIBUTING.md` guidance is not updated automatically. Reconcile it separately with consent.
- To roll back, select `v0.4.0` through the same process, preserving host plans, concept inventories and guidance.

## Known limitations

- The maintainer promoted this release directly from `v0.6.1-beta.2`. The beta exit criteria's live observations were not recorded as part of this release, so live agent compliance with the betas' changes is unverified.
- Railspike is a set of instructions, not technical enforcement. These checks show the instructions are consistent; they do not guarantee every agent will follow them.
- The tag is **annotated and unsigned**. It identifies the revision but does not authenticate a signer.
